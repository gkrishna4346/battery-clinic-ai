2Project overview

The question the project answers

Given how a laptop has been used (its age, charge cycles, daily hours, workload, power draw and temperature), how healthy is its battery?

Battery health is the battery's current capacity as a percentage of the capacity it was designed to hold when new. A new battery is close to 100%; a heavily worn one may be below 40%.

Battery Health (%) ≈ Full Charge Capacity ÷ Design Capacity × 100

That relationship shapes one of the project's most important decisions (section 9.4): if a user already knows the full charge capacity, health is almost a simple division, so by default the model is asked to estimate health without it.

What the tool does

  • Manages its own data: a CSV can be uploaded in the app and checked before it replaces the current data. Every version is kept and can be restored.
  • Trains itself from that CSV and compares 9–11 regression models on 5 different shuffles, ranking them by accuracy and consistency.
  • Lets the user choose the train/test split, whether Full Charge Capacity is used, and which model makes predictions; changes take effect when Apply is pressed.
  • Predicts battery health for one laptop (typed inputs) or many (a CSV), with a health band, an honest error range, insights, what-if suggestions and downloadable CSV and PDF records.
  • Explains itself through this guide and through Mr. GK, an assistant that answers questions about the project.

Who it is for

End users who want an estimate for their laptop, and data scientists who want to understand or extend the modelling. The app hides the modelling details behind sensible defaults; this guide exposes all of them.

3Quick start

Run on your own computer

  1. Install Python 3.11 or newer (Anaconda or python.org).
  2. Create a separate environment so the project's library versions do not clash with other work: 
    conda create -n batterysense python=3.11 -y
conda activate batterysense
  3. In the project folder, install the requirements and start the app: 
    pip install -r requirements.txt
python -m streamlit run app.py
  4. The browser opens at http://localhost:8501. The first start trains all models, which takes around 20–40 seconds; after that, results are cached.

Replace or update the data

  1. Open the Data page (first item in the sidebar) and choose Upload new CSV.
  2. Choose the file. The app shows a check report: missing columns block the upload; values that are not numbers, rows without Battery Health, duplicates and impossible values are listed as warnings. A table compares the new file's medians and ranges with the current data.
  3. Optionally add a version note, then press Replace. The file is saved as a new version, becomes active, and all models retrain.
  4. To go back, pick an earlier version under Version history and press Restore.

Column names must match those in section 6; matching ignores capitals, spaces and punctuation, and extra columns are ignored. Replacing data/battery_health.csv by hand also works: the app notices the change and records it as a new version.

The bundled data file is a stand-in

The project ships with a synthetic 3,000-row file that has the same 11 columns as the real dataset, so the app can be tested. Replace it with the real data before drawing any conclusions.

Deploy online (free tier)

  1. Put the project folder in a GitHub repository (code, data/, docs/, .streamlit/).
  2. Sign in at share.streamlit.io, choose New app, and select the repository and app.py.
  3. The service installs requirements.txt and gives the app a public link.

Free hosting puts the app to sleep after a period without visitors; the next visit wakes it (and retrains, taking about half a minute). This is normal free-tier behaviour. No API keys or external services are used: all modelling runs inside the app.

A note on capacity units

The capacity values in the data are around 40,000–80,000. As milliamp-hours (mAh) that would be roughly ten times a typical laptop battery; as milliwatt-hours (mWh, about 40–80 Wh) it matches typical laptops. The app labels them mAh as in the original design; confirm the unit with the data source and change it in config.py if needed. The unit label does not affect any calculation.

6.2Attribute reference

Battery Age

Meaning
How long the battery has been in use, in years.
Type and role
Whole number; input; treated as a number, not a category (section 9.3).
Why it may matter
Lithium-ion cells lose capacity with time (calendar ageing) even when little used.
Expected relationship
Older → lower health.
Used in
Model input; calculated attribute Cycles per Year.
Caveats
An age of 0 makes Cycles per Year undefined; that value is left blank and filled with the median (section 9.6).

Daily Usage Hours

Meaning
Average number of hours per day the laptop is used.
Type and role
Number; input.
Why it may matter
More use generally means more cycles and more time at elevated temperature.
Expected relationship
More hours → lower health, mostly through Cycle Count and temperature.
Used in
Model input; calculated attributes Heat Stress and Power per Usage Hour.
Caveats
The data does not say whether these hours are on battery or on mains power, which matters a lot for wear.

Gaming User

Meaning
Whether the laptop is regularly used for gaming. Stored as 1 (yes) or 0 (no); the app shows a Yes/No choice.
Type and role
Yes/No; input. Batch files may use 1/0 or Yes/No.
Why it may matter
Gaming creates sustained high power draw and heat.
Expected relationship
Gamers → somewhat lower health.
Used in
Model input; calculated attribute Gaming Load.
Caveats
Self-reported and coarse: it does not say how much or how often.

Design Capacity

Meaning
The capacity the battery was designed to hold when new, from the manufacturer's specification.
Type and role
Number; input.
Why it may matter
On its own it says little about wear; it provides scale for Full Charge Capacity.
Expected relationship
Little direct effect when Full Charge Capacity is excluded.
Used in
Model input; the denominator of the health ratio.
Caveats
Unit uncertain (see the unit note). When Full Charge Capacity is included, these two are analysed as a pair in the insights (section 9.15).

Cycle Count

Meaning
Number of full charge–discharge cycles completed. Two half discharges count as roughly one cycle.
Type and role
Whole number; input.
Why it may matter
Each cycle causes a small amount of permanent wear; this is the most direct usage-based wear signal.
Expected relationship
More cycles → lower health. Typically the strongest input when Full Charge Capacity is excluded.
Used in
Model input; calculated attribute Cycles per Year.
Caveats
Strongly linked to Battery Age, since older batteries have had more time to cycle.

CPU Usage

Meaning
Average processor utilisation, as a percentage.
Type and role
Number between 0 and 100; input. Values above 100 are rejected.
Why it may matter
Higher load means more power draw and heat.
Expected relationship
Mild; mostly indirect through temperature and power.
Used in
Model input; calculated attribute Workload Intensity.
Caveats
An average hides peaks, and the measurement period is unknown.

GPU Usage

Meaning
Average graphics processor utilisation, as a percentage.
Type and role
Number between 0 and 100; input.
Why it may matter
The GPU is among the most power-hungry components.
Expected relationship
Mild; higher among gamers.
Used in
Model input; calculated attributes Workload Intensity and Gaming Load.
Caveats
Laptops without a separate graphics card may report integrated-graphics usage, which is not comparable.

Power Consumption

Meaning
Average power drawn by the laptop, in watts.
Type and role
Number; input.
Why it may matter
Higher discharge rates stress the cells.
Expected relationship
Mild; correlated with CPU and GPU usage.
Used in
Model input; calculated attribute Power per Usage Hour.
Caveats
Partly redundant with CPU and GPU usage, so its individual importance can look smaller than its real effect.

Average Temperature

Meaning
Average operating temperature of the device or battery, in °C.
Type and role
Number; input.
Why it may matter
Heat speeds up the chemical reactions that degrade battery cells.
Expected relationship
Hotter → lower health.
Used in
Model input; calculated attribute Heat Stress.
Caveats
Whether this is battery, processor or case temperature is not documented.

Full Charge Capacity

Meaning
The charge the battery can actually hold today when fully charged.
Type and role
Number; optional input, switched off by default.
Why it matters
It is a measurement of wear rather than a cause: Battery Health is essentially this value divided by Design Capacity.
Expected relationship
Almost deterministic together with Design Capacity (section 9.4).
Used in
Model input only when switched on. When on, its value is also shown as a card beside the prediction.
Caveats
Including it makes scores look excellent but explains little about why batteries wear.

Battery Health (target)

Meaning
Current capacity as a percentage of design capacity.
Type and role
Number between 0 and 100; the value the model predicts.
Bands
Good ≥ 70%, Moderate 40–70%, Poor below 40%. Set in config.py (HEALTH_BANDS); they are domain rules, not something the model learns.
Cleaning
Rows without a Battery Health value are removed before training.
Output handling
Predictions are clipped to 0–100, since health outside that range is impossible.

7Calculated attributes

Five extra attributes are calculated from the inputs. Users never type them; they are computed automatically. Each is a hypothesis about battery wear, so each must earn its place: it is added to the model only if it measurably improves accuracy (section 9.5). Whether or not they are used by the model, all five appear in the How your laptop compares panel, marked ƒ.

Cycles per Year

Cycles per Year = Cycle Count ÷ Battery Age

Separates heavy from light use independent of age: a 2-year-old battery with 1,200 cycles (600/year) has been used far harder than an 8-year-old one with the same count (150/year). Undefined when Battery Age is 0; then left blank and filled with the median.

Heat Stress

Heat Stress (°C·h/day) = Average Temperature × Daily Usage Hours

Heat damages batteries, and long use at high temperature compounds it. This combines both into a daily exposure figure.

Workload Intensity

Workload Intensity (%) = (CPU Usage + GPU Usage) ÷ 2

One combined measure of how hard the laptop works.

Power per Usage Hour

Power per Usage Hour = Power Consumption ÷ Daily Usage Hours

Distinguishes high-power use from simply long use. Undefined when Daily Usage Hours is 0; then filled with the median.

Gaming Load

Gaming Load (%) = Gaming User × GPU Usage

Equals GPU Usage for gamers and 0 for everyone else, isolating sustained GPU load that comes specifically from gaming.

Deliberately not included: the capacity ratio

Full Charge Capacity ÷ Design Capacity × 100 is not offered as a calculated attribute. It is essentially the target itself, so including it would make the model look excellent while learning nothing. This is a form of target leakage.

Attributes worth collecting in future

These are known drivers of battery wear but are not in the current data, so they cannot be used: charging habits (time at 100%, fast charging, deep discharges to near 0%), ambient temperature or climate, laptop brand/model and battery chemistry, screen brightness, and the share of time on battery versus mains power. Charging habits in particular are considered among the strongest factors.

8End-to-end workflow

From the CSV file to a prediction, the data passes through these stages in order. Stages 1–8 run when the app starts, or when the data, the Full Charge Capacity setting or the split changes; stages 9–11 run for each prediction.

LoadRead CSV, detect separator, match column names
CleanConvert to numbers, drop rows without target, remove duplicates
ConfigureApply Full Charge Capacity setting and chosen split
CalculateAdd the five calculated attributes
SelectKeep calculated attributes that improve CV R²
Stability runEvery model × 5 shuffles: train, test, score
RankStability score = mean R² − spread; recommend the top model
Final fitRefit the chosen model on all rows
Validate inputParse, reject impossible values, warn outside range
PredictHealth %, band, likely range
ExplainPercentiles, drivers, conclusion, advice

Inside the model, every prediction also passes through the same preprocessing learned during training: missing values filled with the training median, then standard scaling (section 9.6).

9The pipeline, stage by stage

This section explains each stage: what happens, why, and the exact calculation or rule behind every decision. Function names refer to engine.py.

9.1Loading and validation

Function: load_data, read_csv_any, align_columns

  • Encoding: tries UTF-8 (with or without byte-order mark), then Latin-1.
  • Separator: detected automatically among comma, semicolon, tab and pipe.
  • Column matching: names are compared after lower-casing and removing everything except letters and digits, so Cycle_Count, cycle count and CycleCount all match Cycle Count.
  • Required columns: the nine always-used inputs plus Battery Health. If any is missing the app stops with a message listing what was found. Full Charge Capacity is optional; without it the sidebar switch is disabled.
  • Extra columns are ignored and listed on the About dataset page.

Change detection: the app keeps an internal checksum of the data file (never shown). When the file changes, through Replace, Restore or by hand, all cached results are discarded and the models retrain automatically.

9.2Cleaning

  • Numeric conversion: text such as 1,234 or 45% becomes a number; Yes/No, True/False and Y/N become 1/0. Anything unparseable becomes blank (missing).
  • Rows without Battery Health are removed, since there is nothing to learn from them.
  • Exact duplicate rows are removed, so a repeated laptop cannot appear in both the training and the test part and inflate the score.
  • Missing input values are kept and filled inside the model (section 9.6).
  • Outliers are kept. Extreme but genuine laptops are valid data; tree models are robust to them and scaling limits their influence on linear models.

9.3Data types: why Battery Age is a number

An earlier, generic version of the pipeline treated any whole-number column with 10 or fewer distinct values as a category, a rule meant for coded columns such as a region numbered 1–3. Battery Age (1–10 years) was caught by that rule.

For Battery Age this is wrong, because age is a real quantity: 6 years is more than 5, and each extra year means the same thing. As a category the model would:

  • lose the ordering, and learn each age as an unrelated label with fewer examples per age;
  • be unable to reason about an age it has not seen (for example 11 years);
  • force a dropdown instead of a free-text box in the interface.

Decision: in this project every input except Gaming User is explicitly a number (kind: "numeric" in config.py), and Gaming User is a Yes/No value stored as 1/0. For a yes/no attribute, treating it as a number or a category gives the same result.

9.4The Full Charge Capacity decision

Battery Health is almost exactly Full Charge Capacity divided by Design Capacity. Example from a real row:

44,961.9 ÷ 57,884 × 100 = 77.7%  versus recorded Battery Health 76.9%

The EDA page quantifies this on the current data: the correlation between the ratio and Battery Health, and the median difference between them. When both capacities are inputs, the model mostly learns this ratio. The score looks excellent, but it answers a question the user has already answered by knowing the full charge capacity, and it says little about why the battery wore.

Decision: Full Charge Capacity is off by default, so the model estimates health from usage patterns. The switch in the sidebar lets a user include it, for example when the laptop reports it, and all models retrain. The switch is the first setting in the sidebar because it changes everything downstream.

9.5Calculated attributes: selection

Function: select_engineered

Each calculated attribute from section 7 is tested individually:

  1. Take the training part of shuffle 1 only (seed 11). Test rows never influence which attributes are kept, which avoids leaking test information into the design.
  2. Score the model with only the original inputs using 5-fold cross-validation. The reference model is Hist Gradient Boosting: strong, fast, and able to find interactions.
  3. Add one calculated attribute and score again.
  4. Keep it only if the gain reaches the threshold:
Gain = mean CV R² with the attribute − mean CV R² without   →  keep if Gain ≥ 0.002

If several attributes pass, they are scored together; if the combination is worse than the best single one, only that best one is kept.

Why a threshold: cross-validation scores vary by small amounts from random noise. Without a minimum gain, attributes would be kept for improvements that are not real, making the model more complex for no benefit. 0.002 R² is small but above typical fold-to-fold noise on this data size.

Typical outcome: tree models can often find these combinations by themselves, so few or none may be kept. That is a legitimate result, reported on the Model performance page. The attributes are still used for comparisons in the insights panel.

9.6Preprocessing inside the model

Function: make_pipeline. Every model is wrapped in the same three-step pipeline, learned from the training rows only:

  1. Median imputation: blanks are filled with the training median of that column. The median is used rather than the mean because it is not pulled by extreme values.
  2. Standard scaling: each column is rescaled:
    z = (x − mean) ÷ standard deviation  (mean and standard deviation from the training rows)
    Scaling matters for models that compare distances or penalise coefficient size (K-Nearest Neighbors, Support Vector Regression, Ridge). Without it, Design Capacity (tens of thousands) would dominate Gaming User (0 or 1). Tree models are unaffected by scaling, so it does no harm there.
  3. The model itself.

Because preprocessing lives inside the pipeline, it is re-learned on each training part, so the test rows never influence the medians or scaling. This prevents a subtle form of data leakage.

9.7Train/test split

The data is divided into a training part (the model learns from it) and a test part (hidden, used only to measure accuracy on unseen laptops). The user can choose between four ratios:

OptionTraining shareTest shareTrade-off
70 / 3070%30%Largest test set: most reliable score, slightly less data to learn from
75 / 2575%25%Balanced
80 / 2080%20%Default; common practice
85 / 1585%15%Most training data; test score noisier because fewer rows are tested
What changing the ratio really changes

Mostly how the model is tested, not how good it is. Scores move a little between ratios partly by chance. That is why every ratio is evaluated over 5 shuffles (next section), which makes the comparison far more stable than a single split.

9.8Stability check: 5 internal shuffles

Function: stability_run

A single random split can be lucky or unlucky. Instead of one split, the app repeats the split 5 times with different shuffles, using fixed random states 11, 23, 42, 57, 89 (fixed so results are reproducible). For each shuffle, every model is trained on the training part and scored on the test part. The five scores per model are then summarised:

Mean R² = (R²₁ + R²₂ + R²₃ + R²₄ + R²₅) ÷ 5
Spread = standard deviation of the five R² values
Worst / Best R² = lowest / highest of the five

MAE, RMSE and MAPE are averaged in the same way.

Why the user never picks the random state

If users could change the random state freely, they could keep trying until the score is high and then believe it. The model would not be better; the shuffle would just be lucky. This is a form of cheating the test, even when unintentional. Averaging over fixed shuffles removes that temptation and shows how much the score genuinely varies.

9.11Choosing the recommended model

Models are ranked by a stability score that rewards being both accurate and consistent:

Stability score = Mean R² − Spread (standard deviation of R² across the 5 shuffles)

Example: a model with mean R² 0.930 ± 0.003 (score 0.927) ranks above one with 0.932 ± 0.010 (score 0.922); the second is marginally better on average but less predictable. The top model is marked ⭐ and pre-selected. The user may choose any other model with the option buttons on the Model performance page or the Change model dropdown in the sidebar; both stay in sync. The choice applies immediately to the Predict and Batch pages, and the header subtitle updates to name it. Changing the split or the Full Charge Capacity setting starts a new comparison, so the selection returns to that comparison's recommended model.

9.12The final model

Function: fit_final. After the comparison, the chosen model is trained once more on all rows. The shuffles exist only to measure performance; for real predictions it is better to learn from every available laptop. The reported scores therefore describe this model slightly conservatively, since it has seen 15–30% more data than during testing.

CheckRuleResult

9.14Error ranges shown with a prediction

A regression model does not output a "confidence percentage". Instead, the app reports how wrong the model typically is, measured on test data:

Likely range = prediction ± MAE of the active model (mean over the 5 shuffles)
90% of predictions within ±q: q = 90th percentile of |y − ŷ| over all test rows of all 5 shuffles combined

Example: prediction 76.9%, MAE 1.8 → likely between 75.1% and 78.7%. If q = 3.8, then 9 out of 10 test laptops were predicted within 3.8 points. These are averages over the test data; for inputs outside the training range the real error can be larger.

9.15Insights: conclusion, what-if, step-by-step chart and comparisons

Effect of each input (the basis of all insights)

For each input the app asks: how different would the prediction be if this one input were typical?

Effect of input X = prediction(actual inputs) − prediction(same inputs, with X set to its typical value)

Typical value = the training median (for Gaming User: the most common value). Negative means X lowers health compared with a typical laptop. Calculated attributes are recomputed from the changed input. When Full Charge Capacity is included, it and Design Capacity are tested together, because changing one alone creates an impossible ratio.

From a typical laptop to yours (waterfall chart)

Start = prediction with every input typical  →  add the six largest effects  →  Other inputs & combined effects = your prediction − start − shown effects  →  Your laptop

Because inputs interact, single effects do not add up exactly; the "combined" step makes the total exact rather than hiding the difference.

What if

For each everyday habit that lowers the estimate by at least 0.5 points (INSIGHT_MIN_EFFECT), the app shows the prediction with that habit at its typical value:

What-if prediction = your prediction − effect of that input (at most three are shown)

Habits are the inputs in CHANGEABLE: Daily Usage Hours, Gaming User, CPU Usage, GPU Usage, Power Consumption and Average Temperature. Battery Age, Cycle Count and the capacities reflect history or hardware, so they are named but not offered as what-ifs. A what-if is the model's estimate, not a promise about a real battery.

How your laptop compares

Percentile = (share of laptops with a lower value + ½ × share with an equal value) × 100

Each input is described in words ("higher than 99% of laptops", or "close to typical" between the 35th and 65th percentile) with the typical value beside it, and grouped by its effect: Concerns (lowers the estimate by ≥ 0.5 points), In your favour (raises it by ≥ 0.5) and Normal. The five calculated attributes appear under Usage profile with their formulas.

Conclusion and advice rules

  1. State the prediction and band.
  2. Name up to two inputs with effect ≤ −0.5 points as pulling health down, and the largest effect ≥ +0.5 as working in its favour.
  3. If no input reaches ±0.5 points, say that no single factor stands out.
  4. Mention a calculated attribute only if it is at or above the 80th percentile and one of its source inputs is among the top three negative drivers.
  5. Show advice for the (up to) two negative drivers from ADVICE in config.py.

All insight wording describes associations in the data, not proven causes. The one-at-a-time method is transparent and works for every model; its limitation is that effects of correlated inputs (for example Cycle Count and Battery Age) are not fully separated.

9.16Batch prediction

Uploaded files go through the same column matching and numeric conversion as the training data, then the active model. Blank cells are filled with the training median by the model pipeline and flagged in a Notes column, as are out-of-range values. When the file contains Battery Health, the page reports MAE against those values.

9.17Feature importance

Function: importance_for. Uses permutation importance on the test part of shuffle 1:

Importance of X = R²(original test data) − R²(test data with column X randomly shuffled), averaged over 5 repeats

Shuffling breaks the link between X and health; the bigger the drop in R², the more the model relies on X. This works for every model type. Correlated inputs share credit, so each may look less important than its combined effect. Feature importance is global (across all laptops), while the drivers in 9.15 are local (one laptop).

9.18Data versions

Module: versions.py. Every data file is kept in data/versions/ as battery_health_v<number>_<date>.csv, and versions.json records for each version its number, date, row count, note and how it arrived (initial file, uploaded in the app, or replaced outside the app). The active version is copied to data/battery_health.csv, which the models train on.

  • Replace saves the upload as the next version and activates it. Restore re-activates an earlier version. Nothing is ever deleted.
  • Check before replace (engine.validate_upload): missing required columns or fewer than 30 usable rows block the upload; fewer than 200 rows, non-numeric values, rows without Battery Health, duplicates and impossible values produce warnings.
  • Storage: on your computer, versions stay in the project folder. When deployed, set GITHUB_TOKEN and GITHUB_REPO in .streamlit/secrets.toml; every Replace or Restore is then also committed to the repository, so versions survive restarts and GitHub keeps the full history.
  • There is no password on Replace; any bad upload can be undone with Restore.

9.20EDA statistics

Functions: univariate, outlier_table, vif_table, high_pairs, binned_target in engine.py. Calculated on all rows of the active data version.

Skewness = mean((x − mean)³) ÷ std³  ·  −0.5 to 0.5 symmetric, 0.5–1 moderate, above 1 high; positive = long tail of high values
Kurtosis (excess) = mean((x − mean)⁴) ÷ std⁴ − 3  ·  above 1 heavy tails, below −1 flat (pandas applies small-sample corrections)
IQR outlier: x < Q1 − 1.5 × IQR or x > Q3 + 1.5 × IQR, with IQR = Q3 − Q1  ·  z-score outlier: |x − mean| ÷ std > 3
VIF = 1 ÷ (1 − R²), R² from predicting the input with the other model inputs (linear regression)  ·  below 5 fine, 5–10 moderate, above 10 high
Pearson r: straight-line correlation  ·  Spearman ρ: correlation of ranks, which also captures curved but consistent relationships

"Average health across a variable's range" splits laptops into eight groups of similar size by that variable (each value for Yes/No) and plots the mean health per group. Yes/No variables have no meaningful skewness or kurtosis and are excluded from outlier rules.

9.21Band accuracy: precision and recall

Precision and recall are classification metrics; the model does regression. Because every prediction is also placed in a health band, the app turns actual and predicted health on the test sets of all 5 shuffles into bands and compares them (engine.band_metrics).

Precision (band) = correctly predicted in the band ÷ all predicted in the band
Recall (band) = correctly predicted in the band ÷ all really in the band
F1 = 2 × precision × recall ÷ (precision + recall)  ·  Band accuracy = correct bands ÷ all predictions

Mistakes happen mostly near the 70% and 40% boundaries, where an error of a couple of points crosses the line. A band with no test laptops is shown as "–" because it cannot be measured.

9.22Variable selection: evidence for every variable

Function: variable_decisions. For each variable the app records its role, whether the model uses it, and a justification built from the evidence:

  • Full Charge Capacity: excluded by default because its ratio to Design Capacity correlates almost perfectly with the target (leakage, 9.4).
  • Calculated attributes: used only if the selection test (9.5) shows a gain of at least 0.002 in cross-validated R²; otherwise insights only, with the measured gain shown.
  • Inputs: described as core (|r| ≥ 0.7), useful (0.3–0.7), weak (0.1–0.3, kept for information in combination) or near zero (kept as reference; flagged as a candidate for removal), with VIF, outlier share and the active model's importance.

11Limitations and considerations

About the data

  • Unknown source. How, where and from which laptops the data was collected is not documented. Results describe this dataset and may not apply to other laptop populations, brands or climates.
  • Stand-in data. The bundled CSV is synthetic until replaced with the real file (section 3).
  • Capacity units are uncertain (mAh vs mWh); see the unit note.
  • Measurement definitions (which temperature, which averaging period, whether usage hours are on battery) are unknown.
  • Missing drivers. Charging habits, climate and battery chemistry are not in the data; their effects are invisible to the model or partly absorbed by other inputs.
  • Snapshot, not history. Each row is one moment per laptop; the model cannot track how a single battery wears over time.

About the model

  • Association, not causation. Insights and advice describe patterns in the data. Reducing cycles is associated with higher health; the data cannot prove it will raise any particular battery's health.
  • Extrapolation. Inputs outside the training range produce less reliable predictions; the app warns but does not refuse.
  • Correlated inputs. Cycle Count and Battery Age (and CPU, GPU and power) move together, so their individual importances and effects are partly shared.
  • Fixed hyper-parameters. Models use sensible defaults, not per-dataset tuning; a tuned model could score slightly higher.
  • Error ranges are averages. "± MAE" describes typical test errors, not a guarantee for each laptop.
  • With Full Charge Capacity included, high scores reflect the capacity ratio rather than an understanding of wear.

About running the app

  • No password on Replace: anyone who can open the app can replace the data. Version history makes every change reversible.
  • Mr. GK can be wrong. Answers are grounded in the guide, but AI output can still misread or oversimplify; check the cited section. In AI mode, questions are sent to the AI provider; do not type personal information.
  • Training time: about 20–40 seconds per combination of data, setting and split on a single CPU; results are cached while the app runs.
  • Free hosting sleeps after inactivity; the first visit afterwards retrains.
  • Library versions: the app trains in place, so there is no saved-model version mismatch. If you export a model elsewhere, use the same numpy and scikit-learn versions.

14Glossary

Cross-validation (CV)
Splitting the training data into k parts (here 5), training on k−1 and testing on the remaining one, rotating k times and averaging the scores.
Data leakage / target leakage
When information the model should not have at prediction time (for example the test rows, or a disguised copy of the target) influences training, making scores unrealistically good.
Extrapolation
Predicting for inputs outside the range seen in training.
Feature / attribute
An input column used by the model. This guide uses "attribute".
F1 score
The balance of precision and recall: 2 × precision × recall ÷ (precision + recall) (section 9.21).
IQR (interquartile range)
Q3 − Q1, the spread of the middle half of the values; used for the outlier rule (section 9.20).
Imputation
Filling missing values, here with the training median.
Kurtosis
How heavy a distribution's tails are compared with a normal distribution; above 1 means more extreme values (section 9.20).
Median
The middle value when sorted; half the laptops are below it.
Overfitting
A model that learns the training data too closely, including its noise, and performs worse on new data.
Percentile
The share of laptops with a lower value, as a percentage.
Permutation importance
How much a model's score drops when one attribute's values are shuffled (section 9.17).
Pipeline
A fixed sequence of steps (imputation, scaling, model) learned and applied together.
Random state (seed)
A number that fixes a random process, making a shuffle reproducible.
Precision
Of the laptops predicted in a band, the share really in that band (section 9.21).
R² (R-squared)
The share of the variation in battery health that the model explains: 1 is perfect, 0 is no better than always predicting the average (section 9.10).
Recall
Of the laptops really in a band, the share the model placed there (section 9.21).
Regression
Predicting a number (here health %), as opposed to classification, which predicts a category.
Sensitivity analysis
Changing one input and observing how the output changes (section 9.15).
Skewness
How lopsided a distribution is; positive means a long tail of high values (section 9.20).
Train/test split
Dividing data into a part for learning and a hidden part for measuring accuracy.
VIF (variance inflation factor)
How much an input overlaps with the other inputs: 1 ÷ (1 − R²); above 5 means notable overlap (section 9.20).
Version (data)
One saved copy of the data file, numbered in order; any version can be restored (section 9.18).
Waterfall chart
A chart that starts from one value and adds positive and negative steps to reach a final value (section 9.15).
What-if
The model's estimate after changing one input, all else unchanged (section 9.15).
z-score
How many standard deviations a value is from the mean; |z| > 3 is flagged as an outlier (section 9.20).
